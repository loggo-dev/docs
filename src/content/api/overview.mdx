This is the same HTTP API Loggo's own web UI calls — there's no separate public API surface. It's useful for scripting against a self-hosted instance (bulk importing markdown, automating log creation), but it's **internal and unversioned**: no API keys, no stability guarantee across releases, and every route lives under the app's own origin (`http://localhost:3000` by default).

## Authentication

There's no bearer token — identity comes from which **user** is active in the browser, tracked by the `loggo_session` cookie.

<Badge text="POST" variant="info" size="medium" /> **`/api/auth/login`** sets that cookie: pass an `email` and `password`. Every other endpoint reads the user from the cookie already on the request — script against this API with a cookie jar, the same way a browser session would.

Two permission levels apply, checked server-side on every request that needs them:

| Level | Applies to |
| --- | --- |
| Workspace Member | Reading, creating, editing, and deleting logs, tasks, tags, attachments, and templates within a specific workspace. |
| Admin only | Creating/deleting workspaces, managing users, updating global instance settings, assigning users to workspaces. |

## Conventions

- All request and response bodies are JSON, except file uploads (`multipart/form-data`) and file downloads (raw bytes).
- A failed request returns a JSON body shaped `{ "error": { "message": "..." } }` with a 4xx or 5xx status — there's no separate error-code field to switch on.
- IDs are opaque strings — mostly ULIDs sorted by time.
